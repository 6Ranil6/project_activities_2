ВВЕДЕНИЕ
В современной производственной и торговой среде, где стоимость сырья напрямую влияет на конечную цену продукции и рентабельность бизнеса, оперативный мониторинг цен является ключевой задачей. Рынок металлопродукции отличается высокой волатильностью, и ручное отслеживание цен на десятках и сотнях страниц сайтов-поставщиков является трудоемким, медленным и подверженным ошибкам процессом.
Компания i5.solutions столкнулась с необходимостью автоматизировать сбор данных с сайта одного из ключевых поставщиков 23met.ru для анализа динамики цен и планирования закупок.
Целью настоящей практики являлась разработка программного комплекса для автоматического сбора, обработки и структурирования данных о ценах на металлопродукцию с сайта 23met.ruдля последующего анализа и мониторинга.
Для достижения поставленной цели были определены следующие задачи:
изучить структуру целевого сайта, выявить источники данных и методы их защиты от автоматического сбора;
разработать скрипт для автоматического поиска всех релевантных страниц с прайс-листами;
реализовать асинхронный парсер для эффективного извлечения данных;
создать модуль постобработки для очистки и приведения данных к структурированному виду, готовому для аналиа;
настроить систему для автоматического ежедневного запуска.
Содержание и оформление настоящего отчета осуществлялось с учетом требований ГОСТ 7.32-2017 [1].
1 Анализ предметной области и постановка задачи
1.1 Бизнес-проблема и цели проекта
Ключевой проблемой, решаемой в рамках данной практики, является необходимость в получении актуальных и структурированных данных о ценах на металлопродукцию для компании-партнера i5.solutions. Ручной сбор данных с сайта 23met.ru, являющегося важным источником информации, неэффективен по ряду причин:
Основные компоненты системы:
большой объем данных: Сайт содержит множество разделов и подразделов, каждый с собственными таблицами цен, что делает ручной мониторинг крайне трудоемким;
высокая динамичность цен: Стоимость металлопродукции может меняться ежедневно, что требует постоянного и оперативного отслеживания.
Целью проекта является разработка автоматизированного программного комплекса, который будет выполнять полный цикл сбора, обработки и структурирования данных с целевого сайта, подготавливая их для дальнейшего анализа и использования в бизнес-процессах компании.
1.2 Анализ предметной области
В ходе предварительного анализа сайта 23met.ru были выявлены технические особенности, которые необходимо было учесть при проектировании системы:
cтруктура данных: Вся необходимая информация (наименование товара, ГОСТ, сталь, размеры, цена) представлена в виде стандартных HTML-таблиц, что упрощает их программный разбор;
защита от парсинга: При большом количестве последовательных запросов с одного IP-адреса сайт активирует систему защиты (CAPTCHA), что приводит к временной блокировке доступа. Этот фактор делает обязательным использование механизмов обхода ограничений;
неявная структура навигации: Для полного охвата ассортимента продукции недостаточно простого обхода ссылок с главной страницы. Необходимо было разработать метод для обнаружения всех скрытых или динамически подгружаемых страниц с прайс-листами.

На установочной встрече была определена основная бизнес-задача, стоящая перед компанией, а именно — необходимость в автоматизации сбора и анализа данных о ценах на рынке металлопродукции для оптимизации закупочной деятельности. По итогам встречи было сформировано и выдано техническое задание, в котором были зафиксированы ключевые цели, задачи и требования к итоговому программному продукту.

2 Проектирование архитектуры решения
Для решения поставленной задачи был спроектирован пайплайн, состоящий из нескольких независимых, но последовательно выполняемых модулей:
модуль GoogleParser: Использует внешний сервис ScraperAPI для выполнения поисковых запросов в Google (site:23met.ru прайс-лист). Это позволяет получить полный список URL-адресов всех страниц с прайс-листами, решая проблему их обнаружения;
модуль ProxyParser: Опциональный модуль, который парсит бесплатные прокси-серверы с сайта proxylib.com и проверяет их на работоспособность с целевым сайтом;
основной парсер ParserSite_23MET: Получает список URL-адресов и, при необходимости, прокси. Асинхронно (asyncio, aiohttp) отправляет запросы к каждой странице, скачивая HTML-код. После этого, с помощью BeautifulSoup, он извлекает необработанные табличные данные и сохраняет их в промежуточный CSV-файл (result.csv);
модуль предобработки PreProcessor: Загружает "сырые" данные из result.csv и выполняет их очистку и структурирование. Этот модуль является ключевым для получения качественных данных;
планировщик Cron: Системная утилита Linux, которая по заданному расписанию (например, каждый день в 12:00) запускает главный скрипт main.py, обеспечивая полную автоматизацию процесса.
Для наглядной демонстрации логики работы системы и движения информационных потоков были построены диаграммы потоков данных (DFD) в нотации Йордана. Далее, рассмотрим архитектуру системы с помощью UML-диаграммы классов, который можно увидеть на Рисунке 3. Центральным элементом архитектуры является абстрактный базовый класс Parser. Он определяет общий интерфейс и базовую логику для всех модулей, занимающихся сбором данных. Такой подход позволяет легко расширять систему: для парсинга нового сайта достаточно создать новый класс-наследник, который будет реализовывать специфичную для этого сайта логику.
Класс Parser использует принцип композиции, делегируя низкоуровневые задачи по работе с файлами и сетью специализированным классам-помощникам:
WorkerWithHtml инкапсулирует всю логику отправки HTTP-запросов, работы с User-Agent и прокси;
WorkerWithFiles отвечает за чтение и запись данных в файлы;
оба этих класса реализуют простые интерфейсы Readable и Writable, что соответствует принципу разделения интерфейсов;
от базового класса Parser наследуются три конкретных реализации;
ParserSite_23MET: Основной парсер целевого сайта;
GoogleParser: Парсер, взаимодействующий с ScraperAPI для поиска в Google;
ParserProxyLib: Парсер для сбора бесплатных прокси.
Особняком стоит класс PreProcessor. Он не является парсером и не наследуется от класса Parser, что логично подчеркивает его роль в системе. Его задача — не сбор, а трансформация и очистка уже собранных данных. Он принимает на вход результат работы ParserSite_23MET и преобразует его в структурированный вид.
Такая архитектура обеспечивает высокую модульность, слабую связанность компонентов и хорошую расширяемость, что является залогом надежности и простоты  дальнейшей поддержки проекта.

3 Реализация автоматизированной системы по сбору и обработки данных
3.1 Реализация модуля сбора данных
Модуль сбора данных является центральным компонентом всей системы. Он реализован в виде класса ParserSite_23MET и отвечает за непосредственное взаимодействие с целевым сайтом 23met.ru, скачивание веб-страниц и первичное извлечение из них необработанной информации.
Работа модуля организована в виде последовательного конвейера, состоящего из двух основных этапов:
скачивание страниц (метод save_data): На этом этапе модуль получает список URL-адресов, предварительно собранный модулем GoogleParser. Затем он асинхронно отправляет HTTP-запросы по каждому адресу, скачивает HTML-код страниц с прайс-листами и сохраняет их в локальную директорию 23MET_DATA для последующей обработки. Этот подход позволяет отделить этап получения данных от этапа их разбора, что повышает отказоустойчивость системы: в случае ошибки при разборе нет необходимости заново скачивать десятки страниц;
извлечение данных (метод parsing): После того как все страницы сохранены, модуль последовательно считывает каждый HTML-файл. С помощью библиотеки BeautifulSoup он находит на страницах все таблицы, которые содержат необходимую информацию о продукции. Далее, модуль извлекает нужный текст, который содержит необходимую информацию. Для корректного объединения данных со всех страниц, сперва собираются все уникальные названия столбцов, что позволяет формировать единую структуру данных даже при различиях в таблицах на разных страницах.
Ключевые аспекты реализации: 
асинхронность: Для эффективного и быстрого скачивания большого количества страниц применяется асинхронный подход на базе библиотек asyncio и aiohttp. Это позволяет отправлять множество HTTP-запросов одновременно, не дожидаясь ответа от сервера на каждый предыдущий запрос, что кратно сокращает общее время работы;
ограничение частоты запросов: Чтобы избежать блокировки со стороны сервера из-за слишком высокой активности, используется библиотека aiolimiter. Она позволяет установить ограничение на количество запросов в определенный промежуток времени (например, не более 100 запросов в 10 секунд), что обеспечивает стабильную и вежливую работу парсера.
Центральным методом логики извлечения данных является _parsing_one_site. Он принимает на вход путь к одному HTML-файлу, производит его разбор с помощью BeautifulSoup, находит все необходимые таблицы и преобразует их содержимое в словарь, где ключами являются названия столбцов, а значениями — списки данных. Этот метод также обрабатывает возможные пропуски и несоответствия в структуре таблиц.

3.2 Реализация модуля предобработки данных
           Данные, полученные на этапе парсинга, представляют собой "сырой" набор текстовой информации. Несмотря на табличную структуру, они не пригодны для прямого машинного анализа из-за множества проблем: наличия лишних пробелов, отсутствия стандартизации для пропущенных значений и, что самое важное, наличия композитных полей. Композитные поля — это колонки, в которых в виде одной строки смешано несколько разнородных признаков (например, в поле "Размер" могут быть и габариты и диаметр).
Для решения этой проблемы был разработан модуль PreProcessor (файл preProcessor.py), основной задачей которого является преобразование "сырых" данных в чистый, структурированный и атомарный формат. В качестве основного инструмента для манипуляции данными используется библиотека Pandas, которая предоставляет мощную и эффективную структуру данных DataFrame.
Процесс предобработки представляет собой конвейер из нескольких последовательных шагов:
базовая очистка и стандартизация: Первым шагом является приведение данных к единому стандарту, которая включает в себя удаление лишних пробелов и пропусков;
обработка колонки "Размер" : Данная колонка является самым ярким примером композитного поля. Для ее разбора был разработан статический метод parse_size, который последовательно применяет около десяти регулярных выражений, чтобы распознать различные форматы: Профили по ГОСТ (20К1, 16Б2), Европейские профили (IPE120, HE200A), Габаритные размеры (100х50х4), Листовой прокат с толщиной и размерами (5 1500х6000) и т. д. В результате одна колонка "Размер" порождает до пяти новых: Тип_продукции, Размер_A, Размер_B, Размер_C, Толщина и т.д. Такая декомпозиция критически важна, так как позволяет проводить количественный анализ (например, отфильтровать все листы толщиной более 3 мм), что было невозможно с исходными строковыми данными;
обработка колонки "Сталь": Аналогично "Размеру", эта колонка часто содержит не только марку стали. Метод __process_steel_col извлекает из нее новые признаки. Например: тип материала, основную марку, свариваемость. Это обогащает данные, позволяя проводить более глубокий анализ и сегментацию (например, "сравнить среднюю цену на алюминиевые и латунные изделия").
обработка колонки "ГОСТ" :  Строка стандарта (например, "ГОСТ 8732-78") разбирается на три компонента:  Тип_стандарта (ГОСТ, ТУ), Номер_стандарта (8732) и Год_стандарта (78). Это позволяет фильтровать продукцию по актуальности нормативного документа.

3.3 Реализация механизма кэширования сессий доступа
Ключевым элементом для поддержки механизма обновления токенов является кэширование [7]. Когда сервис watcher-go обрабатывает запрос на обновление, он получает только PLAY_TOKEN и name стрима. Однако для запроса к API партнера требуется полный набор данных (режим, UUID стрима, временные метки и т.д.).
Чтобы решить эту проблему, при первичном обмене QUERY_TOKEN на PLAY_TOKEN приложение на Python сохраняет все необходимые данные о сессии в Redis. Ключ для кэша формируется на основе имени стрима и полученного PLAY_TOKEN.

При запросе на обновление PLAY_TOKEN микросервис на Go извлекает эти данные из Redis по ключу, сформированному из старого токена, и использует их для формирования запроса к API партнера. После получения нового PLAY_TOKEN он кэширует те же данные, но уже с новым ключом.

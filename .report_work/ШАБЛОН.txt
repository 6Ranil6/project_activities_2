В современных условиях рынок металлопродукции характеризуется высокой динамикой цен и широким ассортиментом номенклатуры, что кардинально меняет подходы к закупкам и анализу рынка. Оперативный мониторинг стоимости арматуры, балок, труб и листового проката становится неотъемлемой частью бизнес-процессов строительных и производственных компаний, однако требования к скорости, полноте и достоверности собираемых данных постоянно возрастают. Особую актуальность приобретает обеспечение качественной агрегации информации из разрозненных источников: от поиска актуальных прайс-листов до извлечения специфических параметров (марка стали, ГОСТ, размер) и приведения их к единому стандарту. Такие меры необходимы не только для оперативного планирования закупок, но и для стратегического прогнозирования стоимости проектов.
В большинстве современных рабочих процессов сбор маркетинговой информации о ценах на металлопродукцию выполняется вручную или с использованием примитивных инструментов, что требует значительных временных затрат от специалистов, создает риски пропуска важных изменений и затрудняет стандартизацию данных для последующей аналитики. Кроме того, распространено использование различных форматов представления данных на сайтах поставщиков, что снижает удобство обработки и повышает вероятность ошибок при сведении информации в единую таблицу. Актуальной становится задача разработки специализированного инструмента для автоматической, надежной и структурированной генерации наборов данных о металлопродукции.
Настоящая работа посвящена проектированию и реализации программной системы сбора и обработки данных о металлопродукции, которая обеспечивает автоматизацию ключевых этапов мониторинга веб-ресурсов. Система ориентирована на широкий круг пользователей: аналитиков рынка, менеджеров по снабжению и разработчиков Data Science, нуждающихся в эффективном инструменте для получения «чистых» данных, пригодных для машинной обработки.
В ходе работы были проанализированы современные подходы к веб-скрапингу и существующие решения для автоматизации сбора данных, сформулированы требования к функционалу и отказоустойчивости целевой системы, спроектирована архитектура и реализован программный продукт, который обеспечивает автоматический поиск источников, обход блокировок через прокси-серверы, асинхронную загрузку контента и глубокую предобработку «сырых» данных. Особое внимание уделено алгоритмам декомпозиции строк с описанием товаров (выделение размеров, типов материалов) и механизмам обеспечения надежности сбора данных.
Разработанная система призвана повысить производительность отделов закупок и аналитики, обеспечить прозрачность ценообразования на рынке металлопроката, а также облегчить создание баз данных для последующего статистического анализа и прогнозирования.
В качестве основного языка программирования был выбран Python. Python является одним из самых популярных языков в области сбора и обработки данных, в связи с чем вокруг него сформировалось обширное сообщество разработчиков, и, благодаря этому, существует множество эффективных сторонних библиотек для решения задач веб-скрапинга и анализа данных. Помимо этого, Python обладает лаконичным синтаксисом и высокой скоростью разработки, что позволяет сосредоточиться на логике алгоритмов обработки данных. В данный момент он является наиболее актуальным инструментом для создания парсеров и систем аналитики.
Для реализации сетевого взаимодействия и обеспечения высокой производительности системы была выбрана библиотека aiohttp, работающая на основе асинхронной библиотеки asyncio. Альтернативой является библиотека requests, которая использует синхронный ввод-вывод, но она блокирует выполнение программы на время ожидания ответа от сервера, что существенно замедляет процесс сбора данных при большом количестве запросов. Асинхронный подход позволяет выполнять сотни HTTP-запросов конкурентно, что делает связку Python и aiohttp оптимальным выбором для разработки системы сбора данных.
Для реализации сбора данных из поисковых систем с учетом их ограничений применялся сервис ScraperAPI. Прямое обращение к поисковой выдаче Google сопряжено с жесткими ограничениями на количество автоматических запросов, что делает невозможным стабильный сбор данных без использования сложной инфраструктуры ротации IP-адресов. ScraperAPI берет на себя задачу управления прокси-серверами и обработки заголовков, предоставляя готовый HTML-код страницы, что обеспечивает надежность и отказоустойчивость подсистемы поиска.
Для хранения и обработки табличных данных используется библиотека Pandas. Она предоставляет удобные структуры данных, которые позволяют эффективно фильтровать, очищать и преобразовывать большие массивы информации, а также экспортировать результаты в форматы CSV и Excel, удобные для конечного пользователя.
В качестве среды разработки был выбран редактор кода Visual Studio Code. Его прямым конкурентом при разработке на Python является интегрированная среда разработки PyCharm. Однако полная версия PyCharm является платной, а бесплатная Community-версия имеет ряд ограничений. Visual Studio Code является легковесным редактором кода с большим функционалом и огромным набором пользовательских расширений, что делает его очень гибким инструментом разработки.
Для управления версиями исходного кода и фиксации изменений в процессе разработки была выбрана система контроля версий Git. Использование Git позволяет вести историю изменений, экспериментировать с новыми функциями в отдельных ветках без риска нарушить работоспособность основной версии программы, а также обеспечивает сохранность исходного кода.

Рисунок 3 – Диаграмма потоков данных

Диаграмма отражает следующие ключевые процессы обработки данных:
поиск ссылок на сайты с прайс-листами — инициируется пользователем, в зависимости от флага запуска процесс либо использует существующий кэш, либо выполняет новый поиск, отправляет запросы к Google Search и получает HTML-страницы выдаче, взаимодействует с процессом управления конфигурацией для чтения и корректировки параметров поиска (файл config.json), результатом работы является файл ALL_HREFS.json, содержащий список URL-адресов целевых страниц;
поиск и проверка прокси — запускается при отсутствии флага with_proxy или при необходимости обновления пула адресов, отправляет запрос к внешнему ресурсу proxylib.com и получает список доступных прокси-серверов, выполняет проверку работоспособности серверов и передает список проверенных адресов в процесс парсинга для обеспечения анонимности;
парсинг страниц с веб-ресурса — основной процесс сбора данных, получает на вход список целевых ссылок и опционально список прокси, отправляет HTTP-запросы к целевым веб-ресурсам, получает данные о промышленных изделиях в виде HTML-кода, cохраняет извлеченные неструктурированные данные в промежуточный файл result.csv;
предобработка данных — считывает неструктурированные данные из result.csv, выполняет очистку, нормализацию и структурирование информации (выделение размеров, марок стали, цен), формирует финальный файл preprocessing_result.csv, содержащий готовые к анализу данные.
Такая декомпозиция позволяет четко разделить ответственность между модулями системы: от управления конфигурацией до финальной очистки данных, обеспечивая гибкость и удобство сопровождения программного продукта.
Для отображения физической структуры разрабатываемой системы и связей между исполняемыми модулями, исходными файлами и артефактами данных была разработана диаграмма компонентов. Она демонстрирует, как система разбита на функциональные блоки и какие зависимости существуют между ними.
На рисунке 4 представлена диаграмма компонентов программной системы.

Рисунок 4 – Диаграмма компонентов
Архитектура системы построена по модульному принципу, где каждый компонент отвечает за строго определенную область функциональности:
точка входа (main.py) — центральный управляющий модуль, который оркестрирует работу всех подсистем, он инициирует обновление конфигурации, запускает парсеры в нужной последовательности и передает управление препроцессору;
базовый уровень (Parser, WorkerWithHTML, WorkerWithFiles) — абстрактный слой, реализующий общую логику, компонент Parser предоставляет интерфейс для скрейпинга, WorkerWithHTML инкапсулирует логику сетевых запросов (включая работу с сессиями и ротацию User-Agent), а WorkerWithFiles отвечает за асинхронную работу с файлом (запись/чтение данных);
модули сбора данных — GoogleParser, он специализирован для взаимодействия с поисковой выдачей через внешний сервис ScraperAPI, результатом его работы является артефакт ALL_HREFS.json, proxyParser отвечает за парсинг сайта proxylib.com и формирование пула проверенных прокси-серверов, Parser_23MET является основным модулем парсинга целевого веб-ресурса, он использует список URL-адресов из ALL_HREFS.json и прокси из proxy.json для скачивания страниц и извлечения табличных данных в промежуточный файл result.csv;
модуль обработки (PreProcessor) — компонент, отвечающий за бизнес-логику очистки данных. Он не занимается сетевым взаимодействием, а работает исключительно с файлом result.csv, преобразуя его в финальный артефакт preprocessing_result.csv;
конфигурационный модуль (update_config.py) — вспомогательный модуль для автоматического управления файлом настроек config.json.

Для детального описания внутренней структуры компонентов системы и статических связей между программными модулями была разработана UML-диаграмма классов. Данная диаграмма позволяет визуализировать иерархию наследования, используемые интерфейсы и отношения ассоциации и композиции.
На рисунке 5 представлена диаграмма классов.
Рисунок 5 – Диаграмма классов
В основе объектной модели системы лежит абстрактный базовый класс Parser. Он определяет унифицированный интерфейс и инкапсулирует общую логику инициализации для всех модулей сбора данных. Использование абстракции позволяет легко масштабировать систему: для добавления поддержки нового веб-ресурса достаточно создать класс-наследник, реализующий специфичную для данного сайта логику извлечения данных, не затрагивая основной архитектурный каркас.
Класс Parser реализует принцип композиции, делегируя выполнение низкоуровневых операций специализированным вспомогательным классам:
WorkerWithHtml — класс, отвечающий за сетевое взаимодействие. Он инкапсулирует логику отправки асинхронных HTTP-запросов, управление сессиями, работу с заголовками (User-Agent) и использование прокси-серверов для обхода блокировок;
WorkerWithFiles — класс, предназначенный для асинхронного чтения и записи данных в локальной файловой системе (форматы JSON, CSV, HTML).
Иерархия наследования от базового класса Parser включает три конкретные реализации:
ParserSite_23MET — основной модуль, реализующий логику парсинга целевого веб-ресурса с металлопродукцией;
GoogleParser — модуль, взаимодействующий с API сервиса ScraperAPI для получения ссылок из поисковой выдачи Google;
ParserProxyLib — служебный модуль для сбора и валидации списка бесплатных прокси-серверов.
Отдельно в архитектуре выделен класс PreProcessor. Он не наследуется от Parser, так как имеет принципиально иную зону ответственности — обработку данных, а не их сбор. PreProcessor принимает на вход неструктурированные данные, полученные классом ParserSite_23MET, и выполняет их нормализацию, очистку от шума и приведение к типизированному виду.
Для моделирования динамического поведения системы и визуализации временной последовательности взаимодействия объектов в различных сценариях использования была построена диаграмма последовательности. Она детализирует процесс обмена сообщениями между компонентами системы во времени.
На рисунках 6 и 7 представлена диаграмма последовательности основного сценария работы программы.

Рисунок 6 – Диаграмма последовательности для сбора данных
Рисунок 7 – Диаграмма последовательности для обработки данных
Диаграммы отражают следующий алгоритм работы системы:
инициализация (main.py) — пользователь инициирует выполнение скрипта, вызывая функцию main(), управление передается объекту main.py, который начинает выполнение программы;
cбор прокси-серверов — eсли в конфигурации установлен флаг использования прокси, main.py создает экземпляр класса ParserProxyLib, передавая ему список целевых ресурсов для проверки (checking='23met.ru'), ParserProxyLib отправляет GET-запрос на внешний ресурс proxylib.com, получив HTML-страницу со списком серверов, компонент асинхронно парсит данные, выполняется проверка работоспособности полученных сокетов, валидные прокси сохраняются в локальный файл proxy.json, и их список возвращается в main.py через метод get_sockets();
cбор данных с целевого ресурса — main.py создает экземпляр основного парсера Parser23Met, передавая ему опционально список прокси, вызывается метод run(), который запускает цепочку действий, в первую очередь происходит поиск ссылок на прайс-листы, для этого Parser23Met обращается к компоненту GoogleParser;
поиск источников — GoogleParser формирует поисковые запросы и отправляет их через API-шлюз ScraperAPI для обхода защиты поисковой системы Google, ScraperAPI возвращает готовый HTML-код страниц поисковой выдачи, GoogleParser извлекает из HTML релевантные ссылки на домен 23met.ru и сохраняет их в файл ALL_HREFS.json, cписок URL-адресов возвращается в Parser23Met;
асинхронный парсинг — получив список ссылок, Parser23Met запускает массовую асинхронную загрузку страниц с сайта 23met.ru, для каждой страницы выполняется HTTP-запрос, получение HTML-кода и извлечение табличных данных, все полученные данные объединяются в единый DataFrame и сохраняются в файл result.csv;
предобработка данных — после завершения сбора данных main.py инициирует процесс предобработки, создавая объект PreProcessor, который считывает данные из result.csv, выполняется серия операций очистки, такие как удаление лишних пробелов, замена пустых строк на NaN, обработка колонок «Размер», «Доп. размер», «Сталь», «ГОСТ» и нормализация цен, cтруктурированные данные сохраняются в итоговый файл preprocessing_result.csv;
завершение — программа завершает работу, возвращая управление пользователю.
Диаграммы наглядно демонстрируют использование асинхронных вызовов на этапах сетевого взаимодействия, что позволяет значительно ускорить процесс сбора данных по сравнению с последовательным выполнением запросов.

Система оперирует двумя основными типами данных: «сырыми» данными, полученными непосредственно с веб-ресурсов, и структурированными данными, прошедшими этап предобработки. Хранение осуществляется в формате CSV, что обеспечивает переносимость данных и возможность их импорта в сторонние аналитические инструменты.
Файл result.csv формируется на этапе парсинга HTML-страниц. Он представляет собой денормализованную таблицу, содержащую "грязные" данные, где в одной ячейке могут быть смешаны различные характеристики товара. Основные поля файла:
наименование — исходное название позиции (например, "Арматура А1");
цена — набор колонок с ценами в разных единицах измерения ("Цена, р./т", "Цена, р./шт.", "Цена, р./кг");
размер — текстовое поле, содержащее информацию о габаритах или диаметре (например, "12", "60Б1");
доп. размер — поле с дополнительными характеристиками, такими как длина прута или тип упаковки ("11.7", "бухты");
ГОСТ — строка со стандартом (например, "ГОСТ 34028-2016");
Сталь — марка стали или сплава.
Файл preprocessing_result.csv является результатом работы модуля PreProcessor. В нем произведена декомпозиция сложных полей и нормализация значений.

Процесс верификации программного обеспечения предполагает выбор между двумя фундаментальными подходами: структурным тестированием («белый ящик») и функциональным тестированием («черный ящик»).
Стратегия «белого ящика» базируется на глубоком понимании внутренней архитектуры приложения. Тестировщик, имея полный доступ к исходному коду, алгоритмам и структурам данных, проектирует тестовые сценарии таким образом, чтобы проверить корректность выполнения внутренних логических путей программы. Основная цель данного метода — убедиться, что все ветвления алгоритма, циклы и обработчики исключений функционируют согласно задумке разработчика, а структуры данных инициализируются и используются корректно. Для этого создаются модульные тесты, покрывающие конкретные функции и методы классов.
В противоположность этому, тестирование методом «черного ящика» абстрагируется от внутренней реализации системы. Тестировщик рассматривает программу как закрытый объект, взаимодействие с которым происходит исключительно через внешние интерфейсы (входные и выходные данные). Внимание концентрируется на соответствии поведения системы заявленным функциональным требованиям. Проверка заключается в подаче различных наборов входных данных и сравнении полученного результата с ожидаемым эталоном, игнорируя внутренние механизмы обработки информации.
Чтобы качественно протестировать программу, было решено объединить эти два способа. Метод «белого ящика» использовался для проверки того, правильно ли написан код и как работают внутренние алгоритмы разбора текста. А метод «черного ящика» применялся для проверки конечного результата — правильно ли сформировались таблицы с данными и соответствуют ли они тому, что требовалось получить.
В ходе функционального тестирования (методом «черного ящика») проверялась корректность работы ключевого модуля системы — PreProcessor. Основная цель тестирования заключалась в подтверждении того, что алгоритмы декомпозиции сложных строковых данных (размеров, материалов, цен) корректно обрабатывают как типовые, так и граничные случаи входных данных.

Это обеспечивает более высокое качество и надежность получаемых данных по сравнению с универсальными решениями.

4.1 Требования к функциональным характеристикам

4.1.1.2 Сбор данных с веб-страниц:
асинхронная загрузка HTML-кода по списку полученных URL-адресов;
извлечение табличных данных из HTML-кода страниц;
сохранение извлеченных «сырых» данных в промежуточный файл result.csv.

очистка данных от лишних пробелов и спецсимволов;
приведение пропущенных значений к единому стандарту;
декомпозиция композитных полей на атомарные, машиночитаемые признаки;
агрегация данных о ценах из нескольких полей в единую структуру.
4.1.1.4 Управление конфигурацией и запуском:
чтение внешних параметров из конфигурационного файла config.json;
поддержка запуска в режиме автоматического периодического выполнения программы ПССОДМ по расписанию через Cron.

конфигурационный файл config.json.

автоматический поиск актуальных страниц с прайс-листами через поисковые системы;
cбор и валидация бесплатных прокси-серверов для обеспечения анонимности;
асинхронная загрузка данных, обеспечивающая высокую скорость работы;
интеллектуальная предобработка данных: извлечение размеров, марок стали и цен из текстовых описаний;
cохранение результатов в формате CSV для дальнейшего использования в Excel или аналитических системах.

Для корректного функционирования программного продукта необходимо наличие персонального компьютера или сервера со следующими характеристиками:
операционная система: Linux (Ubuntu 20.04+), macOS 10.15+;
установленный интерпретатор языка Python версии 3.8 или выше;
свободное место на диске: не менее 1 ГБ;
оперативная память: не менее 2 ГБ;
стабильное подключение к сети Интернет (скорость не менее 5 Мбит/с).
Программа не требует инсталляции. Для начала работы необходимо:
скопировать папку с исходным кодом программы на целевой компьютер;
открыть терминал в папке с программой;
установить необходимые библиотеки, выполнив команду: 
pip install -r requirements.txt
Перед первым запуском необходимо отредактировать файл config.json, расположенный в корневой директории программы.
Пример содержимого файла:
{"UPDATE": {
"LAST_CHECKING_DATE": "2023-10-20",
"NEXT_UPDATE": 30
},
"API_KEYS": {
"User_1": {
"API_KEY": "ВАШ_КЛЮЧ_API",
"MAX_CREDIT": 5000,
"USED_CREDIT": 0
}
}
}

Пользователь должен указать действующий ключ API сервиса ScraperAPI в поле API_KEY для обеспечения работы модуля поиска GoogleParser.
Для выполнения разового сбора данных необходимо запустить главный исполняемый файл скрипта. В командной строке выполните:
python3 main.py
В процессе выполнения в консоль будут выводиться сообщения о текущем этапе работы: «Поиск прокси», «Скачивание данных с сайта», «Начинаю предобработку данных».По завершении работы программа выведет сообщение «Работа закончилась» и автоматически закроется.
Для повышения надежности сбора данных и обхода блокировок по IP-адресу предусмотрен режим работы через прокси. Для его активации необходимо открыть файл main.py в любом текстовом редакторе и изменить вызов функции main в конце файла:
asyncio.run(main(with_proxy=True))
В этом режиме программа предварительно соберет список бесплатных прокси-серверов с ресурса proxylib.com, проверит их работоспособность и сохранит в файл PROXY/proxy.json для использования при парсинге.
Для регулярного обновления данных на серверах под управлением Linux рекомендуется настроить планировщик задач Cron.
откройте редактор расписания командой: crontab -e;
добавьте строку для ежедневного запуска в 12:00:
0 12 * * * /usr/bin/python3 /путь/к/папке/main.py >> /путь/к/папке/cron.log 2>&1
В результате выполнения в папке с программой будет создаваться файл журнала cron.log, содержащий отчет о результатах автоматического запуска.
Результатом работы программы являются два файла, расположенные в директории 23MET_DATA:
result.csv — файл с исходными («сырыми») данными, полученными с веб-страниц;
preprocessing_result.csv — файл с обработанными и структурированными данными.
Пользователь может открыть файл preprocessing_result.csv для просмотра цен, фильтрации по маркам стали и анализа рынка.

class Parser(ABC):
"""
Абстрактный класс для парсинга любого сайта.
"""
def __init__(self, base_url: str, proxy_list: list = None):
"""
Args:
base_url (str): доменное имя сайта
proxy_list (list, optional): список прокси, если proxy_list = None, то прокси не будет использоваться, вместо этого при парсинге будет использоваться ваш IP:ПОРТ. Defaults to None.
"""
self.__file_worker = WorkerWithFiles()
self.__html_worker = WorkerWithHtml(proxy_list)
self.base_url = base_url
@abstractmethod
def parsing(self):
pass
@property
def user_agent(self):
return self.__html_worker.user
async def put_file(self, path: str, data: Any) -> None:
"""
Кладет данные в файл
Args:
path (str): абсолютный путь
data (Any): данные
"""
await self.__file_worker.put(path=path, data=data)
async def get_file(self, path: str) -> str:
"""
Берет данные из файла
Args:
path (str): абсолютный путь к файлу
Returns:
str
"""
return await self.__file_worker.get(path=path)
@staticmethod
def get_data_in_file_no_async(file_path: str) -> str:
"""
Получение данных из файла не асинхронным способом
Args:
file_path (str): абсолютный путь к файлу
Returns:
str
"""
return WorkerWithFiles.get_no_async(file_path=file_path)
async def get_html(
self,
session: aiohttp.ClientSession,
url: str,
semaphore: asyncio.Semaphore = None,
accept: str = "*/*",
) -> Union[None, str]:
"""
Получение данных из сайта по переданному вами URL-у.
Args:
session (aiohttp.ClientSession): Сессия
url (str): url
semaphore (asyncio.Semaphore, optional): нужен для ограничения количества запросов. Defaults to None.
accept (str, optional): типы файлов, которые клиент может принять (отображается браузером в header-e). Defaults to '*/*'.
Returns:
Union[None, str]: None если данных нет или не удалось скачать данные из сайта. str - данные из сайта в виде строки
"""
retries = 5 # количество попыток при неудачном запросе
for _ in range(retries):
try:
return await self.__html_worker.get(
session=session, url=url, semaphore=semaphore, accept=accept
)
except:
print("Не вернулся ответ от сервера, пробую еще раз!")
await asyncio.sleep(2)
print(f"Не удалось получить данные с {url} после {retries} попыток. Пропускаю.")
return None
async def _save_data_in_json_file(self, path: str, data: Any) -> None:
"""
Метод кладет json по абсолютному пути path.
Args:
path (str): абсолютный путь к файлу
data (Union[dict, list]): данные, которые нужно положить
"""
await self.__file_worker._put_json_file(path, data)
